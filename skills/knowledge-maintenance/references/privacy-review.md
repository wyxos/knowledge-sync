# Repository privacy review

Read the user's current privacy scope from the connected Knowledge root and applicable authoring/project records. Apply it during ordinary implementation as well as requested audits. Include source, comments, fixtures, filenames, assets, generated/package output, documentation, agent instructions and Git metadata/history within the authorized scope.

Separate portable implementation contracts from private deployment identity, personal/client context and secrets. Use synthetic people, organizations, domains, paths and location choices in public artifacts; replacing an email domain alone does not anonymize a real name. Keep actual deployment configuration in its approved runtime files and credentials in protected stores. Keep durable personal operating profiles, bootstrap content and runbooks in their authoritative private Knowledge home; ignored or untracked project copies do not satisfy that boundary. Public ownership and required dependency references may remain where the current policy allows them.

Before a commit or publication, inspect the actual staged/outgoing diff, new files and included generated artifacts. Review affected images/recordings and asset metadata when relevant. Inspect prospective author/committer identities and outgoing commit messages, and recheck after release tooling mutates output. For public commits, use UTC author/committer dates while preserving their actual instants instead of exposing workstation timezone offsets. Use context and visual inspection as well as searches; a clean tree or a keyword scan alone is not a privacy certification. Do not introduce pattern checks, identity allowlists or Git/CI privacy gates without an explicit request; credential secret scanning is separate.

Apply privacy before automatic-commit or publication defaults. Use an already authorized repository-scoped public identity when available; otherwise complete safe work and report the unresolved identity choice without silently changing global identity or inferring consent from prior commits. Existing-history rewriting requires explicit authorization and review of affected refs, protected recovery, collaborators and remote publication scope. Do not claim old disclosures are removed from third-party clones or caches that were not verified.

Report each supported finding with its location and practical correction. A review request authorizes inspection and recommendations; edits, history rewriting and remote mutations follow the user's actual scope. Preserve unrelated content and verify the corrected disclosure surface when a fix is authorized. State whether verification covered current files, outgoing commits, selected refs or full reachable history; do not generalize a limited audit into a clean-repository claim.
